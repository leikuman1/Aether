# M1 手工检索黄金集

本目录提供 24 篇原创技术说明和 60 条人工构造的查询，供 BM25、dense、RRF 三路检索在同一输入上比较。说明描述真实技术机制，属于手工自建示例，并非抓取的官方文档、生产数据或真实用户日志；没有虚构实测结果，也未依据任一路检索结果修改问题或标签。语料中包含中文说明、英文术语、小节标题与英文查询，覆盖事务、索引、检索、向量、async、重试、安全、可观测、评测和切块。相近概念文档作为干扰候选，例如 B-tree/hash index、TF-IDF/BM25、RRF/reranking、HNSW/IVF、认证/授权与两类 injection。

## 文件与标注约定

- `corpus/`：24 个 UTF-8、LF Markdown 文件。文件名去掉 `.md` 即 `doc_id`。每篇一个一级标题、三个 ATX `##` 小节，每节一个连续正文段落；正文约 100–300 字符，硬上限 480 字符。本版每段同时满足证据长度 80–180 字符。
- `retrieval.jsonl`：60 个独立 JSON 对象，每行一个查询。`id` 为 q001–q060；`query` 是问题；`category` 为下表四类之一；`evidence` 是人工确认的相关证据单元列表；`relevant_chunk_ids` 已冻结为 canonical `markdown-480` 的内容指纹 ID。
- 每项证据含 `doc_id` 与 `text`。`text` 为对应文档正文中逐字出现的有意义原文，本版使用完整小节正文而非关键词集合。多证据列表表示所有列出单元分别相关，不是任选其一。相同文档中的不同小节也可以是独立单元。
- `relevant_chunk_ids` 为非空且必须与证据映射一致，内容变化后旧 ID 会使评测明确失败。fixed 策略在同一证据原文上重新映射：同 doc_id 且包含至少一半连续证据文本（最少 40 字符）才算相关，不以检索结果决定标签。每个不同相关 chunk 计为一个相关项，重叠可能产生多个相关 chunk，因此跨分块 recall 的分母可能不同，数字不能单独用于证明某种切块泛化更好。
- 证据基于技术问题的语义需求与正文内容预先指定；程序只验证文字存在和结构约束，不调用检索器、外部模型或网络。若今后发现漏标，应人工复核全部候选语料并版本化记录，不能看到某条路线返回结果后为了提高该路线分数而追加标签。

## 查询类型

| category | 数量 | 含义 |
| --- | ---: | --- |
| `exact_term` | 15 | 带术语、参数、算法名或接口名的查找 |
| `paraphrase` | 15 | 由用户症状或目标自然改写的提问 |
| `multi_evidence` | 15 | 需要同文档多个小节或跨文档的独立证据 |
| `contrast` | 15 | 比较容易混淆的机制、边界或用途 |

分类是人工设定的主要意图，彼此可能存在语言特征重叠；例如对比问题通常也含精确术语。问题未抄入答案解释，没有为了某个检索器额外向文档添加查询专用别名、重复关键词或同义词表。

## 比较协议与适用边界

固定语料快照、切块器与配置、查询、相关片段集合和最终 top_k，比较 BM25、dense、RRF 的 Recall@k 与 MRR@k，并按四类查询分组报告；多证据查询应特别检查 Recall@k，不能仅依靠首条命中的 MRR 判断充分性。记录分词规则、embedding 版本、距离、各路候选窗口、RRF 常数、延迟采样边界和是否包含编码耗时。去重相关片段并明确多个片段覆盖同一证据时的统计规则，避免把文本重叠制造成额外相关证据。此目录不包含检索得分、阈值承诺或偏向某路的期望胜负。

本集足以进行离线管线回归、证据映射检查及小范围三路比较，不能作为生产语义质量证据。它没有独立保留集、真实流量分布、外部专家一致性标注或统计功效保证，主题覆盖与语言比例也不代表生产用户；同一人工编写过程可能引入风格偏差。不要在这 60 条查询上反复调参再把最终分数宣称为泛化效果。

确定性 FakeEmbedder 只用于无网络、无密钥的接口与流程测试。哈希桶碰撞、词面规则或手写特征不具有真实语义理解能力，FakeEmbedder 下 dense 的得分及其与 BM25/RRF 的相对排名不能外推到真实模型。生产质量需要固定真实编码器、独立标注与真实数据上的另行验证。

## 生成与校验

原始正文和问题由人工逐条构造，临时脚本仅序列化这些固定文本并检查一致性，不随库保存。生成时校验文档数量与三个小节、正文和证据长度、60 个唯一问题与 ID、四类各 15 条、全部证据为对应正文的精确子串，并确认产物均可按 UTF-8 解码、无 BOM、使用 LF。检索结果从未参与标签生成；canonical chunk ID 与 fixed 切块适配由主线程完成。
